[00:03:15] SARAH CHEN: Impressive scale. What were the key trade-offs you considered?

[00:03:22] PRIYA SHARMA: Great question. The biggest trade-off was eventual consistency versus cost. With CQRS, our read path could be up to 30 seconds behind the write path. For most use cases that was acceptable, but for safety-critical alerts, we needed near-real-time. 

So we implemented a dual notification path — critical alerts bypassed the normal pipeline and went through SNS directly to the monitoring dashboard. This added architectural complexity but was non-negotiable for safety.

Cost was another factor. Kinesis Data Streams at that volume was expensive — about $45K/month. We evaluated Kafka on MSK but the operational overhead didn't justify the savings for our team size. We eventually optimized by implementing Kinesis enhanced fan-out only for the critical consumers and standard polling for batch processors, which brought costs down about 30%.

[00:04:45] SARAH CHEN: How did you handle failure scenarios?

[00:04:50] PRIYA SHARMA: We designed for failure at every layer. For Kinesis, we implemented a dead letter queue pattern — if a Lambda processor failed three times on a record, it went to an SQS DLQ with the original payload plus error context. We had a separate reconciliation service that would retry those hourly.

For DynamoDB, we used global tables across us-east-1 and eu-west-1 for disaster recovery. Our RTO was under 5 minutes because the replica was always warm.

The hardest failure to handle was what we called "poison messages" — malformed sensor data that would crash the Lambda function. We implemented a circuit breaker pattern using Step Functions. If error rates for a specific partition exceeded 5% in a 5-minute window, we'd automatically route that partition to a quarantine stream for manual investigation while keeping the rest of the pipeline running.

For chat, I'd use AppSync with GraphQL subscriptions. It handles the WebSocket lifecycle management natively, scales automatically, and integrates with DynamoDB for message persistence.

Video conferencing is the most complex. I'd integrate with Amazon Chime SDK rather than building from scratch. It handles the WebRTC signaling, TURN servers, and media processing. We'd deploy Chime meeting resources in the region closest to the majority of participants using a latency-based routing approach with Route 53.

[00:10:45] SARAH CHEN: What about data isolation and security for the multi-tenant pooled model?

[00:10:52] PRIYA SHARMA: Security is paramount here, especially for enterprise customers. I'd implement defense in depth:

Layer 1 — Network: Each tenant's traffic is tagged at the ALB with a tenant ID header. WAF rules prevent cross-tenant request patterns.

Layer 2 — Application: Every API call includes a tenant context extracted from the JWT. A middleware service validates that the requesting user belongs to the target tenant before any data access.

Layer 3 — Data: PostgreSQL RLS policies automatically filter queries by tenant_id. Even if there's a bug in the application layer, the database won't return cross-tenant data. For sensitive fields, we'd apply column-level encryption using AWS KMS with per-tenant keys.

Layer 4 — Audit: CloudTrail logs enriched with tenant context, shipped to a centralized Security Lake for cross-tenant anomaly detection.

[00:12:40] SARAH CHEN: How would you handle the scaling challenge? 500 customers, peak times could be unpredictable.

[00:12:48] PRIYA SHARMA: I'd approach scaling at multiple levels:

Compute: ECS Fargate with target tracking auto-scaling based on both CPU utilization and custom metrics — specifically, WebSocket connection count per task. I'd set a target of 10,000 concurrent connections per task with a scale-out threshold at 8,000.

Database: Aurora Serverless v2 for the pooled tenants — it scales automatically between 0.5 and 128 ACUs. For the silo tenants, provisioned Aurora with read replicas that auto-scale based on CPU.

Caching: ElastiCache Redis cluster with read replicas. I'd implement a tiered caching strategy — L1 in-process cache (5-second TTL), L2 Redis (60-second TTL), L3 database.

The key insight is pre-warming. For predictable spikes — like Monday morning when all enterprise users log in — I'd implement scheduled scaling actions that pre-provision capacity 15 minutes ahead based on historical patterns analyzed weekly by a simple ML model in SageMaker.
